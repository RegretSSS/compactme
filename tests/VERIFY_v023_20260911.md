## v0.3.3（2026-09-25 修复，17 单测全过，生产验证待第五次自压缩）

### 事故：中文 cwd 转义（jzx pane %6，04:28–04:35，用户报告）

- 症状：「重复发了 N 次压缩命令，但是没发唤醒命令」→ 复核为「唤醒延迟
  很大」（round3 约 04:34:12 送达，任务 04:28 创建，全程 ~6 分钟）。
- 时间线（/tmp/compactme/6/watcher.log + hook 标记）：attempt 1 注入
  04:28:28 → 压缩**真执行**（a7bd9fe4.post ts≈04:30:27 完成）→ 但信号
  全盲 → 90s 超时重注 attempt 2（04:29:59，撞第一次压缩进行中 busy 排队，
  压完执行时 pre≈04:31:30 后无 post——刚压完无可压）→ attempt 3 空转 →
  三轮耗尽 fallback deliver → round1/2 注入撞 busy 期 Enter 未提交
  （dump 铁证：唤醒词全文躺输入框）→ round3 idle 时注入成功送达。
- 根因：Claude Code 的 projects 目录名规则是**非 [a-zA-Z0-9-] 字符每个
  替换成一个 -**（headless 实测：/tmp/试_验.目录 → -tmp-------；二进制
  strings 佐证字符类 [^a-zA-Z0-9-]）。watcher 只做 `/`→`-`：cwd=
  /mnt/d/000-自制软件/建筑信源 算出 `-mnt-d-000-自制软件-建筑信源`，真实
  目录 `-mnt-d-000----------` → active_transcript 目录不存在返 None +
  scan_hook 目录过滤把 a7bd9fe4 的 pre/post 标记全拒 → **双通道全盲**
  （v0.3.1 事故同症，不同根因）。ASCII cwd 下两规则等价，v0.3.2 的四次
  验证全部恰好是 ASCII 路径——盲区潜伏至今。
- 顺手修 log bug：fallback deliver 未传 hint 时 transcript=None，但
  `transcript is transcript_hint`（双 None）为真 → 误打 "(post hook path)"。

### 修复

- `projects_dir_name`：`re.sub(r"[^a-zA-Z0-9-]", "-", cwd)` 对齐 Claude
  Code 真实规则（/-/_/./中文一视同仁；原有 - 保留）。
- deliver_wakeup 的 "(post hook path)" 标注加 `transcript_hint is not
  None` 前置条件。

### 验证

  样本 + headless 实测样本 + ASCII 回归）；test_no_transcript_honest_fail
  加断言 "(post hook path)" 不得出现在 log。
- e2e 未加中文 cwd 模式（e2e 用 COMPACTME_CWD env override，加一例中文

## v0.2.6（2026-09-15 修复，21 单测 + e2e 5/5 全过）

### 发现一：wait_until 布尔化——折叠主路在生产是死代码（真实试用 log 抓出）

- v0.2.5 真实试用（09-13 15:25 pane %3）正常路径成功，但 log 打出
  `text state=True`（预期 `state=text`）——真实 `wait_until` 循环内
  `return True`，只有超时最后一次 `return pred()`；单测 mock 是
  `lambda ...: pred()` 直接返回三态字符串。**单测语义 ≠ 生产**。
- 后果：生产折叠落地必在循环内命中 → state=True → `state == "collapsed"`
  永不匹配 → v0.2.5 的「二次展开」主路在生产从未生效；折叠场景会走
  state=True 误判明文 → 直接 Enter（意外提交 blob = 兜底救法）→
  round2 轮前复查确认 → DONE (delayed confirm)。结果碰巧正确但路径
  与设计不符、多耗一轮退避；e2e paste_collapse 过测靠的正是这条意外
  路径（未断言主路日志，漏检）。
- 修复：`wait_until` 返回使谓词命中的 `pred()` 真实返回值（4 调用点
  核实兼容：truthy 判断 ×2、丢弃返回值 ×1、三态消费 ×2）；单测 mock
  恰与修后首圈行为一致；补 `test_wait_until_returns_pred_value` 直测
  真实实现（`_REAL_WAIT_UNTIL` 在 fast_time mock 前保存）防再失真。

### 发现二：in_input 把提交消息的折行续行误当「文本在框」（e2e 环境变化暴露）

- 症状：09-15 WSL 重启后 e2e 五模式全崩——`after enter, sent=False` +
  nudge「text still in input」×3 → 三轮重发（received.log 每轮都真实
  收到提交，屏幕判据却永假）。git stash 原版 354aa68 复跑同样崩——
  潜伏缺陷，非新代码回归。
- 根因链：昨天 e2e pane 被 attached client 覆盖成 179 宽，唤醒词显示宽
  ~172 列**恰好单行**不折行；WSL 重启后 `-x 120` 生效 → 提交消息折 2 行
  → tail 落到无前缀的折行续行 → 续行又落进底部 4 行窗口 → 旧 in_input
  按「无 ❯+空格前缀 + 含 tail」判「文本在框」→ sent 永假。**漏洞一直
  在，宽度巧合掩盖**（生产 179 宽唤醒词更长必折行，此前成功另有布局
  因素，属踩着巧合过河）。
- 修复：in_input 加**位置判据**——窗口内有输入框提示符行（❯+nbsp）时，
  tail 所在行必须在其下方或同行（输入框折行溢出往提示符下方走；提交
  消息的折行续行在空框提示符**上方**）；窗口内没有提示符行（长文本
  落地态输入区扩展出窗口）退回行级判定，不误伤落地确认。
- e2e 断言加固：paste_collapse 模式必须走主路（log 含 `paste collapsed,
  re-send to expand` 且 end_reason=compacted confirmed 非 delayed）——
  上一版漏检的教训。

### 验证

- 单测 21/21（新增 wait_until 语义直测、折行落窗口回归）。
- e2e 5/5；paste_collapse 主路日志链完整落地：
  `text state=collapsed → re-send to expand → after expand, state=text →

## v0.2.5（2026-09-13 修复，19 单测 + e2e 5/5 全过）

### 事故：pane %2 二次 FAILED（v0.2.4，dump 首次抓到确切现场）

- `/tmp/compactme/2/watcher.log` 04:20:49：三轮 `text landed=False` → FAILED。
  用户手动 Enter 救回。pane %1 同批 04:16 v0.2.4 一轮即中。
- dump 铁证：三轮注入后屏幕依次出现 `[Pasted text #7]`/`#8`/`#9`（编号递增）
  + `paste again to expand` 提示——**文本三轮全部到达**，但被 Claude Code
  按 paste 折叠为占位符，明文永不上屏，tail 落地判据恒假。
- 机制：压缩后 backend 模型未停、继续 busy 跑活（dump 有 todo 更新），
  busy 期到达的大块输入走 paste 排队折叠路径；pane %1/%3 压缩后立即
  idle，走明文键盘路径。09-12 17:00 v0.2.3 的同症失败大概率同因。
- landed=False 按设计不发 Enter → 三轮全空转；实际文本一直在框（折叠态），
  一个 Enter 即可提交——用户手动验证。

### 修复（用户提供两个关键观察：两次 ctrl+v 取消折叠 / 手动 Enter 可提交）

1. **折叠识别**：`deliver_state` 分流 text/collapsed/None——
   `paste again to expand` 提示在屏即折叠（消息流历史 blob 消息不伴提示，
   不误判）。
2. **主路：二次注入展开**：再 send-keys 同样文本模拟「再粘贴一次」
   （官方 paste again to expand 行为），blob 展开为明文（两份拼接，无害），
   走正常 Enter → ❯ 判据。
3. **兜底：折叠 blob 直接 Enter 提交**：展开失败时用用户手动 Enter 的
   救法；成功判据 = 提示消失 + 编号 **大于入口基线** 的新 blob 消息行。
4. **每轮注入前复查 sent**：busy 期 Enter 会被 TUI 排队、模型忙完才提交
   渲染（晚于轮内验证窗口），不复查会重注双发。

### e2e 抓出的假 DONE（paste_collapse 模式第一版）

- 症状：state=DONE (delayed confirm) 但唤醒词 0 次。
- 根因：paste_collapse 全链路下 `/compact` 命令**同样被折叠提交**，其
  blob 消息行（编号 1）> 基线 0，round1 轮前复查把它误判为唤醒词已送达。
- 修复：`prev_max` 改为**入口扫描**屏上实际最大编号做基线（compact blob
  ≤ 基线不参与判定），并补回归测试 `test_entry_compact_blob_no_false_done`。

  TUI 摘要渲染忙期（实证：idle 后注入 727 字符 0.15s 即落地——机制无碍，
  纯时序）；当时无现场 dump，只能推断。

### 修复（用户观察驱动的协议重构）

1. **❯ 判据替代 busy**（用户提出「用户发言灰底渲染」）：成功 = 全屏最后
   一条 `❯ +普通空格` 用户消息含唤醒词 head 且非 `/compact` 前缀。
   字节级实测：**输入框行 = ❯+nbsp(\xa0)，已提交消息 = ❯+普通空格**——
   这是「文本在框」vs「已发出」的可靠区分，不依赖行区域划分
   （压缩刚完成时消息流只有几行，新消息会落进底部 N 行窗口，按区域判必错，
   e2e 实战撞出双发后才修全屏搜）。
2. **BSpace×1200 清框**：C-u 实测无清行语义（727 字符注入后 C-u 原样不动）。
3. **轮前退避 0/3/8s 共 3 轮** + 落地失败 dump 屏幕底部 10 行留痕。
4. split_screen 只删 split artifact 保留真实空行（rstrip 会吃空行致窗口错位）。

### e2e 调试中撞出并修复的坑（fake 保真度）

- fake 输入框折行渲染（v2 的横向滚动模型是错的）+ **底部锚定布局**
  （顶部锚定会让「底部 N 行=输入区」取到空行）
- tmux `new-session -x -y` 会被 attached client 尺寸覆盖（179x50），
  fake 用 ioctl 实际值
- 短唤醒词不折行时 ❯+nbsp 与 tail 同行——in_input 不能排除 ❯ 开头行
  （只能按 nbsp/空格前缀区分）
